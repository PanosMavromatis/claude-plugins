# 01 — memory-check.sh reports each plan file's size and the totals

**Goal**: [x]
> **Done:** `scripts/memory-check.sh` reports a revision's plan files by size, with totals per branch, each naming its layout, and overall. It warns on files read whole that are over the threshold, and writes and gates nothing. It reproduces R1's baseline, ≈16588 tokens.
> **Note:** §4.8 (`tmp/subagent-refactor-plan.md:732`) lists branch indexes among the files a script locates by line, but `/hitl-step` Step 2 reads the index and `goal-file:` whole, and `/smart-merge` step 2 reads the index and then every goal file. The script follows the commands; on this point the design's list is out of date.
> **Q:** §4.8 counts a branch plan's index among the files located by line, reported but never warned on, yet `/hitl-step` and `/smart-merge` read the index whole. Should the script class files by how the commands access them, measuring indexes and single-file branch plans against the threshold like goal files (A), or follow §4.8 and only report indexes (B)?
> **A:** A: files are classed by how the commands access them. A branch plan's index, its goal files, and a single-file branch plan under any root are read whole and measured against the threshold; a master plan and the root index are located by line and only reported.
> **Q:** Should the script take this interface: `memory-check.sh <TODO.md|DO.md> [--threshold <tokens>] [--] [<label>]`; with no label the open revision's directory (ask if several are open), or under a legacy root the root plan and every branch plan under `docs/plan/`, and with a label `docs/plan/<label>/`, open or closed; only plan files (`_TODO.md` by line, a branch's `TODO.md` and `TODO/NN-*.md` whole); a report of `result`, `root`, `layout`, `revision`, `threshold`, `files` (largest first, each with bytes, words, lines, ≈ tokens and its access), `branches`, `total`, `candidates`, `warnings`, `problem`, `fix` and `message`; exit 0 for any report whatever the sizes, 1 for an error, 2 for usage, 3 for a tool that failed (A), or another (B)?
> **A:** A, as proposed. The threshold is in ≈ tokens, applies only to files read whole, and defaults to 4000, the pfsmgraph median from §4.8, until goal 03 sets it from the first R2 goal files.
> **Q:** The report names the root's layout but no branch plan's, so nothing in it says `single-file`. Should each `branches:` line also name its plan's layout, as `feat-plan-locator — single-file, 1 file, …` (A), or is the clause met by classing single-file plans as read whole (B)?
> **A:** A: each `branches:` line names its plan's layout, so the Acceptance clause is checkable and R1's baseline shows at a glance which plans predate the per-goal layout.
