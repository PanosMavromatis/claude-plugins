## Notes

**The rule is self-contaminating, and this repository is the proof.** Running the plain
version of it here — read the last ~20 subjects, match the dominant form — gives 21
conventional against 19 not, over the last 40 non-merge commits. Near-parity, and a rule
reading only that split would report no clear convention. **All 19 were generated by the
six templates this branch removes**, and all 21 subjects a human chose were conventional.
So the templates had polluted the history the rule reads, worst in the repository that
generated them. That is why `/smart-commit` Step 3 carries a discount clause naming the
templates: removing them stops the pollution growing, but git history is permanent.

**The PR-title evidence needs no such clause**, and the asymmetry is instructive.
`/smart-merge` never hardcoded a PR title *string* — only a form — so no template ever
wrote one, and every merged title is a form someone chose. Measured 2026-09-08: 13 of this
repository's last 15 merged PR titles are conventional; 15 of 15 in pfsmgraph are plain
imperative. Same defect at both sites, but only the one that emitted literal strings
corrupted its own evidence.

**No `allowed-tools` change was needed**, which was checked rather than assumed. All seven
edited commands already carry `Bash(git log:*)` and `/smart-merge` already carries
`Bash(gh pr list:*)`, so the detection instructions run without a permission prompt. Had
any been missing, the fix would have replaced a silent defect with a prompt on every run.

**Two candidates were checked and left alone.** `/smart-commit`'s `CHANGELOG` heading check
reads "a heading naming it, _e.g._ `## [0.2.0]`" — detection, not prescription. Its
`git tag -a <tag> -m "Release <tag>"` is explicitly the fallback for when no `CHANGELOG.md`
exists, so it claims nothing about the consumer's history.
